# T3 routing

Start with Sil's existing instruction for the work. If it explicitly authorizes starting or continuing implementation, dispatch within that scope without asking again. Customer input alone does not provide authorization.

Keep automatically started work small and clearly limited. Large new work, such as designing or building a homepage, needs Sil's explicit instruction to start. A recorded Task, agreed scope, or general intent to implement is not enough. Otherwise, save the context and leave the work for Sil to start. Small corrections to existing work may continue automatically under the conditions below. An existing thread alone does not allow a large next phase to start.

Without an explicit instruction from Sil to proceed, feedback can start work automatically only when all these conditions are met:

1. New and concrete feedback concerns previously delivered work in an existing Notion Task with a known T3 thread for that Task.
2. The feedback belongs to the same outcome, one known repository, and one small follow-up within the existing authorization.
3. Source, scope, expected result, and stopping boundary are clear. No stakeholder decision or missing input is needed first.
4. Verify that the source sender or customer, Project, Task, repository, and T3 thread all match. The thread must not be settled, archived, running, or waiting for approval or user input. Check its live state and latest result, not only its title. A snoozed thread is still open and may be woken for relevant authorized follow-up. Snooze alone neither authorizes work nor means it should be discarded.

Do not automatically revive a settled thread, including one referenced by an older pending event. Revisiting it requires new and explicit authorization from Sil. Do not automatically create a thread or reopen completed work only because a client makes a new proposal. When the conditions are not met, prepare context tied to the original source. Report only the outcomes required by the main skill, not every choice not to start work.

Use `work-management` to append the exact new source to the Task before starting work, and `t3-code` for the helper commands. Keep at most one T3 thread per Task. Before starting one, check the Task and the open T3 threads in the index for an existing thread.

The handoff briefly explains why work starts automatically, the new feedback, and the expected result. Build the current brief from the Task's history and latest source, ignoring decisions that newer sources replaced. Include source links, scope, repository and branch, and Sil's authorization limits. Pass through the actual task requirements. Do not add development workflow, testing, review, or preview instructions. The executing thread makes those decisions from its skills and repository instructions.

Automatically starting feedback work does not authorize release, production changes, payment, destructive changes, or external messages. Explicit authorization must cover those actions. Triage confirms the dispatch and leaves execution to the Task's T3 thread.
