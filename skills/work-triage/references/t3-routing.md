# T3 routing

Start from the user's existing instruction for the work. If it clearly allows starting or continuing implementation, dispatch within that scope without asking again. Customer input alone never allows it.

Keep automatically started work small and clearly bounded. Large new work, such as designing or building a homepage, needs the user's explicit instruction. A recorded Task, an agreed scope, or a general intent to implement is not enough; save the context and leave the start to the user. An existing thread does not allow a large next phase either.

Without an explicit instruction, feedback may start work only when all of these hold:

1. New, concrete feedback concerns previously delivered work in an existing Notion Task with a known T3 thread.
2. The feedback belongs to the same outcome, one known repository, and one small follow-up within the existing approval.
3. Source, scope, expected result, and stopping point are clear. No stakeholder decision or missing input is needed first.
4. The sender or customer, Project, Task, repository, and T3 thread all match. The thread is not settled, archived, running, or waiting for approval or input. Check its live state and latest result, not only its title. A snoozed thread is still open and may be woken for approved follow-up. Snooze alone neither allows work nor means it should be dropped.

Do not revive a settled thread on your own, also not one referenced by an older pending event. That needs new, explicit approval from the user. Do not create a thread or reopen finished work just because a client proposes something new. When the conditions are not met, save the context tied to the source. Report only the outcomes the main skill asks for, not every decision not to start.

Use `work-management` to append the new source to the Task before starting, and `t3-code` for the helper commands. At most one T3 thread per Task. Before starting one, check the Task and the open threads in the index for an existing one.

The handoff says briefly why work starts automatically, what the new feedback is, and what result is expected. Build the brief from the Task's history and latest source, ignoring decisions that newer sources replaced. Include source links, scope, repository and branch, and the user's limits. Pass the actual requirements through. Do not add development, testing, review, or preview instructions; the thread decides those from its skills and repository instructions.

Automatically started feedback work does not allow release, production changes, payment, destructive changes, or external messages. Those need explicit approval. Triage confirms the dispatch and leaves execution to the thread.
